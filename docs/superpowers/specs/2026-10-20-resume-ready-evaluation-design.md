# RepoEvidence：简历可用真实性能与问答评测设计

## 目标

建立能复跑、可审计且不夸大能力的开发者评测。它必须分别回答：真实 Agent 的证据问答是否达标、引用是否正确、全量与增量索引各需多少时间，以及快照/变更检测安全性是否保持。

## 现状

现有 `make eval` 只对预先填写的 fixture 回答和引用运行确定性规则；它不会检索、不会请求 Agent，也不测量延迟。因此不能作为“真实回答准确率”或“RAG 性能提升”的唯一证据。

## 方案

采用混合评测：

1. 保留 `make eval` 作为零成本 CI 回归门禁；
2. 新建至少 30 条有人工标准行级证据的题目，调用真实 HTTP 会话链路；
3. 用确定性临时 fixture 运行三次全量与三次单文件增量索引基准；
4. 将已有快照保护、变更检测、无效引用拦截测试作为可靠性证据。

不采用 LLM-as-a-judge：它会增加费用、偏差和不可复现性。在线问答只在开发者显式运行时调用配置的模型。

## 评分规则

每条真实回答由人工金标准评分：

- **引用准确率**：回答中可解析的 `path:start-end` 引用里，落在任一期望范围的比例；没有可用引用即为 0。
- **引用覆盖率**：期望证据范围中至少被一条回答引用覆盖的比例。
- **概念通过率**：是否包含该题全部必含术语（忽略大小写）。
- **严格任务通过率**：准确率、覆盖率、必含术语均 100%，且未引用禁止路径。
- **端到端延迟**：从提交消息到会话终态的 wall-clock 时间；只对真正完成并有答案的样本计算 P50/P95。

它们只代表“指定提交、指定题集、指定模型和指定环境”下的证据问答表现，不是模型的普适准确率。

## 数据与隔离

题库必须至少 30 条，覆盖 `architecture`、`configuration`、`call-chain`、`snapshot`、`error-boundary`、`tool-boundary` 六类。每个引用范围在当前源码中可验证。

原始问题、模型回答、会话 ID、事件、绝对路径和供应商内容只写入已忽略的 `artifacts/evaluation/`。提交到 `docs/quality/` 的摘要只包含聚合分数、样本数、失败 ID、题集哈希、运行日期、方法和局限性，绝不包含密钥或原始输出。

## 命令

| 命令 | 模型调用 | 用途 |
| --- | --- | --- |
| `make eval` | 否 | 保持原有确定性 CI 门禁 |
| `make benchmark-index` | 否 | 三次全量/增量索引性能基准 |
| `REPO_EVIDENCE_RUN_ONLINE_EVAL=1 make eval-online` | 是 | 30 题真实 Agent 评测 |
| `make evaluate-resume` | 是 | 顺序运行全部评测，手动使用 |

在线命令执行前必须检查服务健康、目标仓库状态为 `ready`、collection 是当前快照、题集至少 30 条；不满足时必须失败，不能降级为 fixture 成绩。

## 索引基准

基准只在程序生成的临时 Python/TypeScript/Markdown/YAML 仓库上运行，并使用假 embedding/本地向量写入模拟，不读用户仓库且不访问网络。报告记录 fixture 文件/chunk 数、运行次数、全量/增量中位数与 P95、复用文件数、变更文件数和加速比。

## 简历表述

结果生成后可按报告实际数值使用：

> 为本地代码仓库 RAG 构建 30 题证据评测集；在 [模型]、[日期] 的固定环境下，严格任务通过率为 [x%]，引用准确率/覆盖率为 [x%]/[y%]，端到端 P50/P95 为 [x]/[y] ms。

> 实现基于不可变快照的增量索引；在 [文件数] 个文件、三次固定 fixture 基准中，全量/单文件增量索引中位数为 [x]/[y] s，增量加速 [z] 倍；代码变更会使旧索引失效，同时保留历史证据回看。

不能选取单次最快值、忽略失败题目，也不能省略样本数和测试环境。

## 验收标准

1. 题库至少 30 题，六类均覆盖，并有源码范围校验。
2. 测试覆盖题库校验、引用解析、聚合统计、P50/P95、在线前置检查与摘要脱敏。
3. `make ci`、`make eval` 仍然不读取模型密钥、不发在线请求。
4. `make benchmark-index` 产生三次全量、三次增量报告。
5. 在线命令对 30 个真实会话逐条产出终态结果；失败不伪装为成绩。
